# 未命名冒险：产品与生成方向

> 记录于 2026-08-29。本文描述下一阶段产品方向，不代表当前版本已经实现。

## 一句话定义

让 LLM 用用户保存过的数字遗迹，生成一场只有这组收藏才能长出来、直到通关后才被命名的冒险。

这不再是“把收藏夹套进复古电脑、废弃医院、地下实验室等预设风格”。系统可以选择更跳脱、更意识流的表达，也可以不预设统一主题。核心惊喜是：用户事前无法预料这些互不相干的书签会被编成怎样的场景、物件和事件，事后又能看懂创意从何而来。

## 核心判断

1. **主题不是生成前必须回答的问题。** 固定风格会过早收窄模型的想象空间，也容易迫使互不相关的书签服从虚假的统一世界观。
2. **无主题不等于无结构。** 世界观和场景转换可以意识流，事实边界、交互反馈和通关逻辑必须严格。
3. **允许意义延迟出现。** 冒险可以先发生，玩家在通关后再为它命名；LLM 的解释只能作为候选理解，不是标准答案。
4. **意外感来自具体变形，而不只是换皮。** 书签应被转化为物件、规则、证词、天气、动作或场景之间的因果，而不是统一加一层题材文案。

## 创作边界

### 可以自由虚构

- 书签在冒险中的化身和所在空间；
- 场景之间梦境式、蒙太奇式或非地理连续的转换；
- 反复出现的声音、颜色、动作、符号和句式；
- 玩家在世界中的身份、任务和最终选择；
- 对真实收藏事实进行隐喻和重新编排。

### 不得虚构

- 网页正文、参数、日期、数字、人物或结论等输入中不存在的��实；
- 无法由标题、域名、URL 路径、文件夹、收藏时间、描述或重复收藏记录核查的谜题答案；
- 为了让统一主题成立而伪造书签之间的内容关系。

设计纪律可以概括为：**世界可以做梦，证据不能做梦；叙事可以跳跃，交互不能含糊。**

## 隐藏的创作结构

系统不向玩家展示主题选择，而是在生成阶段形成一份隐藏创作计划，包括：

- creativeThesis：冒险的内在命题，不直接展示给玩家；
- adventureGrammar：组织跳跃素材的冒险语法；
- recurringMotifs：反复出现的声音、动作、符号或材质；
- surpriseTurns：一至两个重新解释旧事件的转折；
- forbiddenClaims：本次生成不能越过的事实边界。

creativeThesis 应约束场景、状态变化和结局，在体验中被感知，而不是由开场文案直接说明。

## 冒险语法

模型可以选择或混合少量隐藏语法，让跳跃素材仍有可感知的组织方式：

- **变形**：每条书签使用后变成另一件东西，最终形成一件完整物品。
- **朝圣**：场景彼此不连续，但每处都会留下同一种符号或动作。
- **审判**：书签分别成为证人、证词、伪证和缺席者。
- **失忆**：完成一步后，旧物件的名���或意义发生变化。
- **官僚迷宫**：盖章、归档、退件和移交构成谜题动作。
- **梦境接力**：上一场景的动作，在下一场景成为环境规则。
- **错误宇宙**：系统把无关收藏误认成同一个项目，玩家决定是否让错误成为现实。
- **无中心选集**：局部书签两两构成小冒险，结局才暴露它们共享的行为轨迹。

这些语法是生成器的内部工具，不能作为模板名显示给玩家，也不应固定对应某类书签。

## 母题代替强制主题

当收藏缺乏统一语义时，不强求“所有物件都服务于同一题材”，而使用重复母题建立潜在连贯性。母题可以是声音、动作、形状、材质、数字变化或一句不断变形的话。

主题要求解释“这些东西为什么属于同一个世界”；母题只要求玩家逐渐感觉“这些经历彼此在押韵”。后者更适合跳跃、私人且偶然的收藏记录。

## 惊奇预算

每次冒险只安排一到两个真正改变理解的转折，其余规则保持稳定、可学会、可预测。

- 不要求每个物件都反转；过多反转只会显得随机。
- 转折应重新解释玩家已经做过的动作，而不是凭空加入新设定。
- 干扰项可以在结局成为叙事证据，但不得事后��写为必需谜题道具。
- 最强的意外不是“模型突然编了怪故事”，而是玩家发现怪故事确实从自己的收藏事实中长出。

## 延迟命名体验

1. 开场只显示“未命名冒险”或中性编号，不提前公布主题。
2. 首页取消固定密室风格，最多保留抽象程度、情绪强度、禁用元素等非剧透边界。
3. 通关后先让玩家输入自己的标题，避免被模型答案锚定。
4. 再展示 LLM 给出的三个候选标题，每个代表一种不同理解，但不宣称标准答案。
5. 玩家可以保留自己的标题、选择候选或合并标题。
6. 最后解锁“冒险回执”，说明真实书签事实分别如何转化为物件、事件和母题。

冒险回执是事后可解释性的主要载体。体验过程中不剧透，结束后证明创意不是随机拼贴。

## 生成管线建议

将现有“一次调用决定主题、文案和谜题”的职责拆开：

1. **事实提取**：生成可核查的素材事实表，并标注哪些字段可用于谜题。
2. **创作计划**：生成隐藏命题、冒险语法、母题和惊奇预算，不生成具体答案。
3. **场景编排**：允许局部配对、跳跃场景和非中心结构，确定状态变化如何跨场景传递。
4. **谜题生成**：只基于事实���生成 beats、机关和交付链。
5. **双重验证**：验证结构可解性与事实可追溯性；前者由共享引擎规则和真实 DOM 保证，后者由逐项来源记录保证。
6. **结局生成**：生成候选标题和冒险回执，但在通关前保持隐藏。

创作计划可以一次生成少量候选并本地评分，重点不是主题一致性，而是：意外但不随机；可由输入事实事后解释；不强行声称无关书签内容相关；能自然支持观察、组合、回访、机关和交付；与近期生成结果有足够差异。

## 产品界面方向

首页主动作改为“生成一次未命名冒险”。固定主题下拉框不再是主流程。可选约束仅包括：

- 抽象程度：清晰 / 游移 / 梦境；
- 情绪强度：轻盈 / 克制 / 强烈；
- 禁用元素：恐怖、医疗、封闭空间等；
- “不要问我任何问题”：完全由系统决定。

这些选项只约束表达边界，不直接指定主题或故事。

## 质量标准

1. **可通关**：真实引擎能完整执行，刷新恢复不破坏状态。
2. **可追溯**：每个关键线索、答案和创意转化都能回指输入事实。
3. **不可预先穷尽**：第一幕不能泄露全部后续变形和结局。
4. **事后成立**：玩家读完冒险回执后能理���创意来源，而不是只觉得随机。
5. **有节制的惊奇**：最多一到两个核心转折，基础交互规则稳定。
6. **允许不统一**：低关联素材不因缺少单一主题而被判为设计失败。

## 与当前方案的关系

当前固定风格、三场景模板和事实锚定规则可以保留为兼容或兜底路径，但不再代表产品上限。下一阶段的关键迁移是：

- 从“生成前选主题”转向“通关后命名”；
- 从“主题一致性”转向“母题回响 + 事后可解释”；
- 从“统一空间外壳”转向“冒险语法组织跳跃场景”；
- 从“LLM 给玩家一个答案”转向“玩家先解释，LLM 再提供候选理解”。

这条方向的独特价值不在于生成更多密室皮肤，而在于让用户第一次看见：自己曾经随手保存、彼此无关的页面，也可以被组织成一场无法由别人的收藏复制的冒险。

## 空间架构观察：多场景不等于多房间

当前生成器虽然能够输出多个 scenes，但运行时体验仍是根节点下面依次出现场景 1、场景 2。根因不是 LLM 缺少空间想象力，而是现有 schema、编译器和引擎都把 scene 定义成按顺序解锁的章节，而不是可探索的空间。

### 当前模型实际表达的结构

现有 scene 最终只保留标题、描述、核心装置文字、物件列表和步骤列表。它没有表达房间父子关系、门与走廊、邻接方向、容器嵌套、空间可达性、回访路径或并行分支。focus 只是文案，不会生成真正的容器节点。

编译器还会自动把前一场景最后一步焊接为后一场景第一步的前置；引擎的 revealScene 会隐藏其他场景，只显示当前场景；advanceScene 则在当前场景全部步骤完成后切到下一幕。因此当前结构本质上是：

根节点 → 线性剧情控制器 → 场景 1 步骤组 → 场景 2 步骤组 → 场景 3 步骤组。

它拥有空间名称和空间文案，但没有空间行为。画布坐标也只是视觉排布，不参与可达性、遮挡、入口、移动或探索顺序。

### 与原作空间感的差异

原作的空间感来自递归节点树与局部发现：房间里有桌面，桌面里有抽屉，抽屉后有暗格；门连接另一个房间；旧空间会保留并可回访；解谜改变的是空间状态，而不是简单切换到下一章。

当前 scenes 路径只有一层：关卡 → 场景 → 物件。项目已有的 compiled-container 容器能力只在无 scenes 的旧分支使用，新的 LLM scenes 路径没有接入容器树。这是已有执行能力与生成路径之间的断层。

### 目标模型：scene 与 space 分离

不要继续给 scenes 增加职责。scene 可以保留为叙事章节或节奏分组；新增独立的空间图层，至少表达：

- spaces：房间、走廊、表面、柜体、抽屉、暗格等递归空间节点；
- parent/children：空间包含关系；
- connections：门、通道、楼梯、暗门等邻接关系；
- lockedBy/discoveredBy：空间何时可进入或被发现；
- currentSpace/discovered/open：运行时空间状态；
- effects：步骤对空间执行 open、unlock、reveal、move、transform 等效果。

beat 应操作空间状态，而不只是给素材 id 增加 clue。一个钥匙与抽屉的组合，应产生打开抽屉和显露纸条两个空间效果；进入走廊应由门的连接状态决定，而不是由 sceneIndex 加一决定。

### 建议的四层边界

1. 叙事层：creativeThesis、母题、转折和章节节奏。
2. 空间层：spaces、containers、connections、可见性与可达性。
3. 谜题层：beats、requires、uses、effects 和产物。
4. 运行层：currentSpace、discovered、open、clues、物件状态和存档。

LLM 应生成空间图和局部谜题关系；编译器验证空间图连通、门禁可达、隐藏空间有发现路径、容器层级无环；引擎负责呈现当前空间及已发现的邻接空间，并允许回访，而不是一次只保留一个场景。

### 改造完成标准

- 同一时刻可以存在多个已发现、可回访的空间节点；
- 至少支持房间 → 家具或表面 → 容器 → 道具的三层递归探索；
- 门和通道是运行时实体，具有锁定、开启和通往目标空间的状态；
- LLM 可以设计分支、汇聚、回环和隐藏房间，不被���动压成 scene 1 → scene 2；
- 场景章节可以推进叙事，但不能替代空间可达性；
- 存档必须恢复当前空间、已发现空间、容器开闭和连接解锁状态；
- 真实 DOM 验证要覆盖进入、返回、打开容器、发现暗格和跨空间使用产物。

这项改造的核心判断是：模型目前生成的是多房间文本，编译器执行的是线性章节；项目尚未定义真正的空间。

## 内容 Grounding 观察：为什么谜题退化为域名和路径元数据

2026-08-29 对生成结果“未命名冒险 · 08-29 09_29.room.json”的审查表明，当前谜题主要依赖标题、域名、URL 路径和日期，而不是网页具体内容。这不是单一的 LLM 能力问题，而是内容供给、提示词示范和验证闭环共同造成的结果。

### 已确认的因果链

1. **主生成路径没有网页正文。** 当前 app.js 的 generate() 在选出六条素材后已移除 fetchMetaInto() 调用，只给设计模型补充 urlPath；样本六条素材的 description 也全部为空。
2. **现有网页富化能力本身不足。** fetchMetaInto() 对服务端返回值只使用 title/meta description；服务端只读取 HTML 前 64KB 并提取 title 与 meta，不能稳定处理正文、列表、代码或动态渲染页面。因此即使重新打开它，也不等于网页研究。
3. **Prompt 主动把模型推向元数据。** 当前设计指令把标题词、域名、文件夹、日期和 URL 路径数字列为推理材料，并把路径数字称为最佳原料。没有正文时，模型自然会把路径数字包装成密码、编号或设备刻字。
4. **Few-shot 示例示范了人工虚构线索。** 监狱和熊曰示例中的日记、摩斯表、熊字表、便签密文是人工关卡道具，不是网页研究结果。它们能教会模型写组合链和机关，却没有教会模型从网页抽取证据、引用原文、不得声称页面上不存在的内容。
5. **校验器只验证结构和机械可解性。** 当前检查会验证 scenes、uses、deliver、机关参数和 solver 结果，但不会检查 reason 中的“页脚/卡背/批注”等断言是否存在于网页正文，也不会要求密码引用具体原文。

样本中的“页脚印着路径数字”“卡背写着取第 2、4、6 位”“卡片角落印着五十音行序号”等文案正是这种机制的结果：模型从真实元数据得到数字，再把它们物理化成输入中并不存在的页面或道具事实。

### 对轻量 harness 的判断

给 LLM 一个网页搜索工具有潜力，但单独增加搜索工具不够，甚至可能让模型先编谜题、再搜索材料为既定谜题辩护。正确顺序应是：

研究原始收藏页面 → 记录证据包 → 设计冒险 → 语法/事实检查 → 修正 → 通关验证

最小 harness 可以先提供 inspect_bookmark、search_web（原页面不可用时才用）、record_evidence、check_level、repair_level 和 simulate_level。其中最关键的是 record_evidence，而不是搜索本身。

证据必须区分三类来源：用户收藏的原始页面、研究阶段找到的外部页面、模型根据来源整理的事实。外部搜索结果参与谜题时，冒险回执应明确标注其来源。

### 最小有效修复

不必立即实现完整 harness。第一轮只做以下四项：

1. 选出六条素材后恢复网页富化调用；
2. /fetch-meta 返回受限的正文 excerpt 和 contentStatus，而不只是 title/meta description；
3. 将 pageExcerpt 单独传给设计模型，Prompt 改为网页内容优先，元数据仅作身份或备用线索；
4. 为关键谜面增加轻量 evidenceRefs/quote，本地检查引用是否出现在 pageExcerpt 中。

如果 pageExcerpt 为空，模型不得虚构页脚、卡背、批注、说明书或页面参数，只能使用确实存在的标题、域名、路径、文件夹和日期，并在回执中标注为 metadata-only。参考关卡里的日记、对照表和密文应明确标注为机制示例，不能复制为当前网页事实。

先做元数据模式与正文摘录模式的 A/B 比较：正文命中率、关键 beat 的正文引用比例、metadata-only 谜题比例、玩家理解度和真实 DOM 通关率。只有确认普通摘要不足时，才升级到浏览器渲染、页面替代版本和搜索研究。

正文会被发送给外部 LLM，因此界面必须明确告知用户并允许拒绝；只读取选中的六条页面，不保存完整网页，只保存受限摘录、来源状态和必要引用。

最终原则是：**世界可以做梦，证据不能做梦；模型可以搜索，谜题必须留下来源。**

## 生成耗时优化观察：先减少重复工作，再调整模型

2026-08-29 的性能审查判断，当前生成耗时主要来自设计模型调用、重复发送大 Prompt、供应商赛马、内外层重试和服务端 advisor 重试；本地解析、编译和求解通常不是主要瓶颈。优化目标应是在不牺牲内容 grounding、空间想象和创作自由的前提下减少重复推理。

### 推荐的优化顺序

1. **备用供应商延迟启动。** 先启动历史上更快或成功率更高的一路；只有主路在首包或完成预算内没有进展时才启动备用路。主路通过后立即取消备用路，避免每次都支付两份完整设计调用。
2. **拆分短规划与受约束展开。** 先用短调用确定素材角色、证据、核心机制、空间骨架和转折；再用较短调用展开场景文案与 beats。第二步不重新思考全局结构，局部失败只修对应 beat。
3. **压缩 Prompt 和 few-shot。** 删除重复规则，参考关卡只保留最能示范目标机制的片段；修复轮只发送错误摘要、相关素材和必要上下文。若供应商支持，启用静态前缀的 Prompt caching。
4. **把机械字段移出 LLM。** id、场景编号、selectedItemIds、mechanics 汇总、timeline、默认 hints、布局坐标和简单 deliver 收尾由本地生成；模型只负责创意判断、证据引用、空间关系和谜题链。
5. **从整版重试改为局部修复。** JSON 字段错误、缺 deriveFrom/resultOn、单个机关参数错误和单步 solver 卡点不应重新设计整关；只有空间骨架或核心创意失败时才整版重试。
6. **收敛 advisor 重试。** 不应仅因为响应没有特定的 `[Advisor consultation]` 文本块就重发上游。应由结构检查、事实检查或真实执行失败触发修复，并集中定义最多一层的 advisor/模型重试预算。
7. **按阶段设置推理预算。** 清洗、证据抽取、JSON 修复、标题和回执使用低成本/低推理配置；创作计划使用中等配置；核心谜题设计才使用高质量配置。输出长度也应按实际 schema 限制。
8. **建立分层缓存。** 分别缓存网页摘录、证据包、创作计划、最终关卡和校验结果；缓存键必须包含对应的内容、Prompt、参考关卡、编译器和检查器版本。
9. **研究请求并发且有预算。** 恢复网页研究后，六条选定页面可并发读取，总预算控制在 10-15 秒；单页超时就标记 `contentStatus: empty` 继续，不应拖住整关。
10. **增加阶段遥测。** 记录 parse、clean、research、首 token、模型耗时、Prompt token 数、provider、repair 次数、上游尝试次数、缓存命中、获胜路线和取消路线，区分模型慢、排队慢、代理重试和前端等待。

### 最小高收益组合

若只做一轮小改动，优先做：备用供应商延迟启动；移除基于 advisor 文本标记的无条件上游重跑；压缩重复 Prompt；将整版修复改成局部修复；增加阶段耗时和真实上游调用次数遥测。

若只能改一项，先改服务端 advisor 重试策略；若能改两项，再加备用供应商延迟启动。这两项最可能直接消除重复的完整模型调用。不要简单地把所有阶段切换到低质量模型，也不要为了缩短耗时移除网页证据和事实校验。

### 验收约束

性能优化后仍须比较生成质量：总耗时 P50/P95、模型调用次数、Prompt token、内容证据引用比例、metadata-only 比例、结构/事实校验通过率和真实 DOM 通关率。任何降耗方案若让 grounding 或创作质量明显下降，不应作为默认策略。

## 内容呈现与原网页探索：从信息墙回到线索

2026-08-30 对生成结果“未命名冒险 · 08-30 05_15.room.json”复盘后，发现网页内容已经进入收藏素材，但没有进入谜题证据链；同时，原始描述被直接拼接到节点详情，造成信息墙。样本中的 description 混有中、英、日文、作者账号、播放统计、导航文案和 URL 信息；beat 的 `evidenceRefs` 仍为空，机关只通过 `deriveFrom` 指向整条书签。

### 信息加工层

网页抓取结果不应直接作为玩家文案。应经过一层内容编译：去除播放量/点赞数/账号/导航等噪声，检测语言，生成短中文摘要，保留原文引用，并提取少量可用于谜题的 `sourceFacts`。建议事实结构包含 `originalQuote`、`displayText`、`locator`、`kind`、`confidence` 和可用的 `affordances`。

关卡中的 `reason` 只负责当前谜面；`sourcePreview` 负责短来源摘要；`originalQuote` 负责可折叠复核；`evidenceRefs` 负责证明谜面实际使用了哪些事实。`deriveFrom` 只指向书签 id，不足以证明“页面写着什么”，不能替代具体证据引用。

grounding checker 至少应要求关键 beat 有 `evidenceRefs`，引用事实存在，谜面中的关键数字/断言能在引用摘录或机器可验证的推导中找到。建议跟踪内容利用率、证据覆盖率和 metadata-only 比例。

### UI 信息层级

节点详情应分为三层：

1. **当前谜面**：化身名、当前状态和一到两句玩家此刻需要理解的线索，默认可见。
2. **来源证据**：折叠区显示短中文摘要、来源标题、域名和一小段原文；完整 URL、路径和长 description 默认隐藏。
3. **原网页操作**：详情卡中提供明确的“打开原网页”按钮，必要时附带“去页面确认启动命令/找到分类表/查看制作名单”等具体观察目标。

英文、日文和其他原文先以中文摘要服务解谜，原始语言作为可展开的复核材料。URL 只有在成为谜题证据时才显示，并高亮实际使用的短片段。

### 鼓励玩家打开原标签页

打开原网页应成为有目的的探索动作，而不是详情底部的通用链接。关卡可以生成 `externalTask`，包含观察目标、答案形式、接受答案和来源证据；玩家打开原页面后回来填写短答案、选择结果或继续操作。核心谜题必须有保存摘录兜底，因为页面可能失效、变化、需要登录或无法渲染。

建议分三级：核心线索不能依赖在线页面；增强线索打开网页更容易但有摘录兜底；奖励探索提供额外故事、视觉素材或彩蛋但不阻塞通关。可以监听 `visibilitychange` 识别玩家回到游戏并更新“来源已回访”状态，但不要把它当作玩家确实读完页面的证明。

这条设计的核心是：**摘要服务于解谜，证据服务于信任，原网页服务于探索。** 网页内容不应被原样倾倒到详情卡，也不应只作为模型看过但玩家永远用不到的隐藏输入。

## 状态管理观察：重置必须区分房间、本关和存档

2026-08-30 复查发现，UI 顶部“重置房间”按钮调用的是基础 `roomReset()`，而生成关卡专用的重置逻辑被放在另一个 `reset()` 包装函数中。点击按钮后，基础函数会清空 `compiled` 并重新克隆原生 Room 02 节点，因此生成关卡消失、画布只剩固定“收藏室”；但工具栏标题、`currentLevel` 和 IndexedDB 进度仍保留旧关卡上下文，形成 UI、运行态和存档三者不一致。

这是架构问题，不应继续靠函数包装顺序修补。产品必须明确区分：

- **重置本关**：清空当前运行进度，保留当前关卡、主题、空间结构和存档记录，重新回到本关入口；
- **离开本关**：保存当前进度并返回标题界面；
- **删除存档**：显式确认后删除 `levels` 与 `progress`；
- **恢复本关**：从版本化快照恢复全部运行状态。

统一入口应为 `resetCurrentLevel()`，由 UI、快捷操作和测试共同调用；基础 `roomReset()` 只能负责底层节点克隆，不能被直接绑定到产品按钮。

重置/恢复快照至少需要处理：机关弹窗上下文、当前空间/已发现空间、容器开闭、物件 hidden/used/morph 状态、sequence/inspect 中间态、hint 状态、并行房间模式和视图缩放/平移。离开或切换关卡时还要停止自动保存和命名轮询，避免旧任务继续写入新关卡。

## 动画观察：节点展开不是 keyframe 参数问题

2026-08-30 复查节点展开动画后确认，当前实现实际上只有节点的淡入、缩放和轻微位移，并没有“从父节点向空间槽位展开”的动画。动画不稳定的主要原因在渲染生命周期：节点在渲染前已经被放到最终坐标，`roomRender()` 又通过 `innerHTML` 整体替换 DOM；多个同步渲染还会在浏览器首次绘制前清掉 `justArrived`/`justChanged`。

具体问题：

1. `levelStart()`、`revealAllRooms()`、`revealScene()` 和 `inspect()` 可能在同一调用栈中连续触发 `roomRender()`；后一次渲染会替换前一次带 `.arrive` 的节点，动画尚未绘制就消失。
2. `roomRender()` 每次删除并重建所有节点，CSS 的 `left/top transition` 没有旧 DOM 状态可供插值，因此节点只会瞬移到最终位置。
3. `roomLayoutBoard()` 在首次渲染前直接计算最终坐标，所以即使保留 DOM，也没有“父节点附近 → 目标槽位”的起始位置。
4. `.node` 有两段 `transition` 声明，后段覆盖前段，导致最初声明的 `left/top` 过渡失效。
5. `morphNode()` 同时设置 `justArrived` 与 `justChanged`，`.changed` 的完整 `animation` 会覆盖 `.arrive`，状态变身时两套动画不能同时工作。
6. 某些通用 reveal 路径只把 `hidden` 改为 false，没有同步 `revealed`，节点仍可能保留 `compiled-hidden-item` 的 `opacity:0/pointer-events:none` 类。

改造顺序：先把状态更新与渲染合并为一次提交，并用 `animationend` 清理动画状态；再改为 keyed DOM 更新或 FLIP 位置过渡；随后补上真正的展开动画（父节点起点、目标槽位和 stagger 延迟）；最后合并 CSS transition，并为 arrive/changed 使用独立动画属性。

动画验收必须覆盖：首次进入关卡、房间显形、容器显形、隐藏物回访、物件变身、错误操作后的再次显形、桌面与移动端，以及 `prefers-reduced-motion`。验收不应只看最终节点是否存在，还要确认动画类在首次绘制前没有被二次渲染清掉、节点没有瞬移、邻近节点和详情卡不被动画遮挡。

## 生成等待体验：把黑盒等待变成可感知的工作过程

当前生成流程是“点击生成 → 等待 LLM → 完整关卡通过后才显示游戏”。`generate()` 在完成前不会挂载中间结果，设计请求使用非流式响应，页面主要只有状态文字；因此用户无法判断系统是在排队、研究、生成、重试还是已经卡住。

建议将生成过程设计为一个“生成中的工作台”：

- 立即显示阶段步骤和已用时间：读取收藏夹、选出素材、研究页面、编排空间与谜题、检查可玩性、整理回执；
- 展示已经确定的六条素材、来源读取状态、当前生成路线、重试次数和简短的事实性活动日志；
- 生成完成前显示不可交互的预览骨架，让用户看到房间、物件和母题逐步形成，但不要把未经验证的半成品伪装成正式关卡；
- 显示供应商赛马状态，例如某一路生成中、某一路已返回正在校验、某一路因结构错误被淘汰；
- 提供取消生成、返回标题界面、查看已选收藏和打开来源页面的能力；取消必须终止在途请求，并阻止旧结果写入当前关卡或缓存；
- 允许在等待期间进行低风险探索，例如查看选中的来源，但不要让用户修改尚未完成的关卡状态；
- 等待过久时提供明确的“继续等待完整版本 / 切换快速版本”，快速版本必须保留内容证据、结构检查和可玩性检查，不能静默降级；
- 长期可将生成任务后台化，用户可以离开工作台，稍后从任务列表返回生成结果。

不要显示虚假的百分比，也不要展示模型原始思维链。进度应来自真实阶段事件和已完成工作，活动日志应描述系统事件而不是编造模型正在思考的内容。

最小 MVP：生成中独立面板、阶段步骤、已用时间、六条素材预览、事实性活动日志、取消按钮、赛马/重试状态和不可交互的布置预览。性能验收同时记录总耗时、首个可见进展时间、调用次数、取消成功率和最终质量，不以“更快但更差”为成功。

## 谜题面板溢出观察：动态内容不能用固定定位估算

2026-08-31 复查密码、角度和摩斯面板后，发现“偶尔溢出屏幕”来自动态内容、锚点定位和视口约束之间的不一致，而不是谜题逻辑错误。

- `openPuzzlePanel()` 只根据锚点节点判断左右位置，没有在显示后测量面板实际高度，也没有检查 bottom 是否超出视口；角度面板因表盘数量动态变化最容易从底部溢出。
- JS 用约 340px 估算宽度，CSS 实际使用 `min(330px, calc(100vw - 36px))`，两套尺寸来源不一致；画布缩放/平移和移动端布局会进一步放大偏差。
- 密码颜色标签、长 kicker/title 和长摩斯串都是动态内容。`.code`/`.kp-slot` 缺乏完整的 shrink/wrap/截断约束，按钮行与标签可能把卡片横向撑开。
- 面板显示后不使用真实 `getBoundingClientRect()` 做重新定位，只尝试右侧/左侧，没有右上、右下、左上、左下四向候选。
- 通用 `.modal-card` 与 `.puzzle-panel .modal-card` 分散定义，后续样式变更容易产生覆盖和断点不一致。

最小修复：显示后测量真实宽高；使用 viewport 而不是固定舞台估算做四向避让；动态设置最大高度和宽度；为 `.code`、`.kp-slot`、颜色标签和摩斯按钮增加 `min-width:0`、换行和长度上限；移动端使用 `100dvh` 和更小边距；集中谜题面板样式。

验收必须覆盖桌面底部节点、移动端密码面板、长标题/颜色标签、长摩斯串、三个角度表盘、画布缩放/平移和虚拟键盘导致的可视高度变化。不能只检查面板存在，还要检查四条边均在视口内、确认/关闭按钮可见可操作。

## 生成结果复盘：硬规则为何仍退化为开锁链

2026-08-30 横向复盘三份生成结果：`未命名冒险 · 08-29 12_32.room.json`、`未命名冒险 · 08-29 14_22.room.json`、`未命名冒险 · 08-29 16_12.room.json`。三份结果都只有 2 个 scenes、约 7 个 beats，没有 `parent`、`exits`、`connections` 或真正的 `containers` 空间拓扑；动作主要是 inspect + password，combine 最多一次，甚至有一份完全没有 combine。

### 根因：系统在奖励最低限度合规

1. **硬规则只约束数量，不约束语义。** `combineCount >= 1` 只能迫使模型塞进一个组合，不能要求组合改变空间状态、打开容器、显露新线索、成为后续步骤的必要条件，或与另一条物品链汇合。模型因此选择最便宜的象征性组合。
2. **Prompt 默认范式就是开锁链。** 设计指令反复强调 password/angle/morse、expected、deriveFrom、resultOn 和 deliver，核心示范是“观察 → 组合 → 推理锁 → 交付”，却没有同等强度地要求工具作用、容器打开、物件多状态、空间回访和非锁定操作。
3. **scene 仍是章节分组，不是空间。** schema 没有 parent/children/connections/door/container/position 等字段；focus 只是文字。编译器把场景变成 `compiled-level` 下的兄弟节点，`parallelRooms` 也只是同时显示这些 sibling，不会产生房间内层级。
4. **已有容器能力没有接入 scenes 路径。** `compiled-container-*` 主要存在于旧平铺分支；LLM scenes 路径仍然是“场景 → 物件”一层。hidden 只表示素材稍后显形，不代表“家具 → 抽屉 → 暗格”的递归探索。
5. **网页正文仍未进入设计输入。** 三份样本的 description 全为空，模型收到的仍主要是 title、domain、urlPath、folder 和 dateAdded。它没有真正可理解的网页内容，只能围绕域名数字和路径出题。
6. **few-shot 示范的是人工虚构道具。** 监狱和熊曰示例能示范谜题链，但日记、摩斯表、熊字表和便签密文都是作者预设的机关材料，不是网页研究证据。模型学到的是“把 URL 记录变成道具上的人造线索”。
7. **验证器只判断结构和机械可解。** 它不判断 combine 是否有实际用途、场景是否存在空间关系、密码是否来自网页内容，也不衡量玩法是否只是重复开锁。因此增加硬规则后，模型会做约束投机，而不是提升冒险设计。

这组结果说明：问题不是 LLM 不听硬规则，而是硬规则、schema、示例和验证器共同定义了一个“能通过的最短路径”。当前最短路径就是四次观察、一次或两次密码、一次可选组合和交付。

### 后续改造边界

短期内容实验可以先恢复正文 excerpt、改为正文优先、增加 evidenceRefs 和最小引用校验；但这不能解决空间层次。空间改造必须另外引入 `scene` 与 `space` 分层，以及 `connections`、递归容器和 beat effects。

在完整空间图完成前，玩法实验至少应要求：

- 至少两种具有实际语义差异的操作类型，而不是仅增加 action 数量；
- 每个 combine 必须改变物件或空间状态，并被后续步骤实际使用；
- 至少一条工具 → 容器/遮挡物 → 隐藏物的发现链；
- 至少一个可回访的旧节点，其状态变化影响后续操作；
- password/angle/morse 不是默认高潮，只有网页事实自然支持时才使用；
- solver、grounding checker 和真实 DOM 验证分别检查可执行性、证据真实性和玩家体验。

轻量 harness 的职责也应从“给模型一个搜索工具”扩展为：先研究原始页面，记录证据，再提出多种机制，最后检查语法、玩法语义、事实来源并模拟执行。仅增加搜索工具，可能只会让模型用更多外部材料包装同一种开锁链。
